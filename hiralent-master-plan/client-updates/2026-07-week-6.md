## What got done this period

**We fixed the single biggest thing standing between this app and real traffic.**

Every part of the server that talks to the database used to open its **own private line** to that database — over **eighty separate places in the code**, each spinning up its own set of connections. A database only allows so many connections at once. So while the app worked fine for one or two people, under real load — a few hundred people using it at the same time — those lines would pile up, hit the database's ceiling, and the whole system would seize up. One screen was even opening a brand-new connection *on every single click*.

We rewired the **entire server to share one properly-managed database connection** instead. Concretely:
- We found **every** place in the code that opened its own line (83 files) and pointed them all at one shared connection manager.
- We did the risky part first: we converted a small, representative handful by hand and confirmed the app still compiled perfectly, *then* rolled the change out everywhere — so we never gambled the whole change at once.
- We added an **automatic guard** that permanently blocks anyone from re-introducing the old pattern. If a developer ever opens a private database line again, the build fails and tells them to use the shared one. We deliberately tried to sneak the bad pattern back in to confirm the guard actually fires — it did.

**How we know it's real:** the whole server still compiles cleanly, and we started it up against a real database and confirmed it runs — health check green, a real sign-up-and-log-in journey works live, and unauthorized access is still blocked.

**Then we put firm limits on that shared connection — the part that actually protects against overload.**

Sharing one connection manager was step one; step two is telling it *how many* database connections it's allowed to hold, so it can never flood the database no matter how busy the app gets. We set a firm cap (10 connections per running service) and did the math so that all seven of our background services combined stay comfortably under the database's ceiling. We also added the standard piece of infrastructure ("PgBouncer" — a traffic controller that lets many users share a few database connections); it's now defined and ready, and gets switched on when we move to the live-hosting phase.

**How we proved the cap actually holds — not just "we set a setting":** we wrote an automated test that hammers the running server with dozens of simultaneous requests and then *counts the actual open database connections in real time*. It confirmed the server holds exactly at the cap and never goes over — both in a controlled stress test and against the real, fully-booted application handling 30 sign-ups at once. This is a genuine load-behavior proof, not just a checkbox.

Our full automated safety suite is now **25 checks, all green** (up from 23).
