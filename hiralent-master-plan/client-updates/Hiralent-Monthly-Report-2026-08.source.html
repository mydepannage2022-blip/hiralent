This month we took Hiralent from an application that could not even be built or run to one that builds cleanly, runs end-to-end, is secured, is able to handle real numbers of users, has every user type's screens genuinely working, and can now take real card payments.

The work was deliberately done in order, from the foundations upward. You cannot secure an app that will not start; you cannot deploy an app that is not secure; you cannot take money on an app that is not correct. Five of the nine planned stages are now finished and independently verified. A sixth — real payments — is about two-thirds done.

The three things worth knowing

1. The product itself is in far better shape than a month ago.

Payments were completely fake — the "pay" button produced an invented receipt and no money ever moved. Real card checkout, real receipts, refunds, upgrades and plan limits are now built and tested. Security holes that would have let an outsider log in as any user, including your administrator, are closed. The app previously would have fallen over with a few hundred people using it at once; that ceiling has been removed.

2. The deployment date moved from the 10th to a revised window.

We committed to having it deployed by the 10th. It is the 20th and it is not deployed. We owe you a straight explanation, and Section 5 of this report gives one in full — including the attempt we made, what we found, and why we chose to stop rather than push through. Your public website is, however, already live on your main domain today.

3. The revised commitment: 10–15 days.

The remaining payment work finishes first, then we deploy once, properly — not a temporary test deployment that has to be torn down and repeated. Section 7 sets out the plan day by day.

Section 4

What we completed this month

Six blocks of work, in the order they were done.

01

Making the application build and run at all

This sounds basic; it was the single biggest blocker. Neither half of the system could be prepared for a real server — the website had 222 blocking errors and the server 153. There were also two competing installation tools fighting each other, which is the classic cause of "it works on my machine but not on yours".

  • All 375 blocking errors fixed properly — not hidden by switching off the safety checks.
  • Several of them turned out to be real bugs waiting to happen: the "recommended jobs" screen, part of the CV upload, the "verifying your email" step and a photo-in-chat feature would all have failed for real users.
  • Settled on one installation tool so every machine and the live server install exactly the same versions.
  • Removed about 15 dead files and a duplicated password library that was a genuine hazard.
  • Found and neutralised a configuration line that, in the wrong circumstances, could have wiped the main database.
  • Ran the whole system together for the first time and proved a real sign-up and login works live.
02

Security

The review found several issues that individually would have been enough to stop a launch.

  • Anyone could have logged in as anyone. The secret key used to sign logins was left at its factory default, publicly known. That means a stranger could have created a valid login for your administrator account. Rotated and locked down.
  • A live API key was sitting in the code, visible to anyone with access to the project, and billable to you. Revoked and replaced with a secure setup.
  • Candidate code could escape onto the server. The coding-test feature had a fallback that ran a candidate's submitted code directly on the main server. Closed, and later replaced with a properly isolated executor.
  • Private data was reachable without logging in — CVs, code submissions, and a document-verification callback that could have been faked to approve identity checks. All now require proper authentication.
  • One candidate could view or edit another candidate's profile simply by changing a number in the address bar. Fixed across every affected screen.
  • Sign-up allowed anyone to register themselves as an administrator. Removed.
  • Added standard web-security protections, request rate limits, shorter login lifetimes, and proper sign-out.
How we check ourselves

After each block of work we deliberately re-examine our own changes as if an outside auditor were trying to break them. That habit found and fixed a further 25 real issues this month that the original work had missed — including six ways money could have been manipulated once payments went in.

03

The database — making it survive real traffic

Every part of the server was opening its own private line to the database — in over 80 different places. A database only permits so many at once. The app was fine for a handful of people and would have seized up with a few hundred.

  • Rewired the entire server onto a single shared, capped connection — and added an automatic guard so the old pattern can never come back.
  • Proved it under stress: we fired dozens of simultaneous requests at the running server while counting the actual live connections. It held at the cap and never went over.
  • Added 36 database indexes to the busiest tables so large lists stay fast as data grows — measured, not assumed.
  • Added limits so a single request can no longer ask for the entire database at once.
  • Fixed data-model faults: postal codes could not accept letters, qualifications were stored in three places that drifted apart, and deleting a user was blocked by 44 broken links between tables.
  • Removed an unused database that the server nevertheless refused to start without.
  • Made a brand-new database usable in one command — correct structure, an admin account, plans and starter data — which is exactly what a live deployment needs.
04

Fixing the things that looked like they worked

This category is the most dangerous kind of bug, because nothing shows an error — the screen simply does nothing, and users assume they did something wrong.

  • Users were being silently signed out roughly every 15 minutes. The app was misreading the server's "here is your refreshed session" reply. Fixed.
  • The administrator's agency-approval screen was entirely non-functional — it displayed, but approve, reject and list all failed silently. Fixed.
  • "Sign out of other devices" did nothing — the feature was fully built but never connected. Connected.
  • Document-verification results were being sent to the wrong address and quietly discarded. Fixed and proven end-to-end.
  • Chat had no live updates for read-receipts and reactions — the server sent them, the app never listened. Now live, with read ticks.
  • Sign-up emails could fail silently, leaving users stuck unverified with no clue why. Failures are now visible.
  • The app had the developer's local address hard-coded in about 47 files. Moving to a real server would have meant hand-editing dozens of files. Now it is a single setting.
  • Introduced one consistent way for the server to reply and to report errors, so a failure surfaces as a clear message rather than a blank screen.
05

06

Real payments — about two-thirds done

This was the single largest fake area of the product. The old checkout produced a made-up reference and a made-up receipt URL; no card was ever charged and no subscription ever really started.

  • Real hosted card checkout is live, with prices taken from the database rather than trusted from the browser — so a customer cannot alter what they are charged.
  • Payment confirmations are cryptographically verified before an account is upgraded, and recorded so the same confirmation can never be processed twice.
  • The full lifecycle works: upgrade, downgrade with fair proration, cancel now or at period end, refunds, failed-payment handling and automatic expiry.
  • Plan limits are enforced for real — job posting and AI interview allowances now come from the customer's actual plan.
  • Receipts cannot be altered or deleted, enforced at the database itself, and a read-only reconciliation view lets you compare our records against the payment provider's.
  • Payment methods we are not launching with are honestly disabled rather than shown as broken buttons.
  • Still to do: billing for agencies (they have different needs from companies, so they get their own plans), and a final end-to-end money test.
Section 5

The deployment date — what happened

We said deployment would be done by the 10th. It is the 20th and it is not done. That commitment was not met, and this section explains exactly why — without softening it.

What we actually tried

We did not simply let the date pass. Between the 15th and the 19th we opened a parallel track specifically to get the system onto a live test server while development continued, so that you could see and click through a working deployment. That track got a long way:

  • The server was packaged for hosting for the first time (this had never existed).
  • An automatic release process was written and proven on a fresh, empty database — it sets up the database, creates the admin account, and then verifies that it actually worked rather than assuming.
  • A safe set of demo accounts was built so you could log in as each user type and try the product.
  • Hosting credentials and a full click-by-click deployment guide were prepared.

Then we stopped, deliberately, and moved that work back to its proper place in the sequence.

Why we stopped — five honest reasons

1. Deploying half-finished payments is the one thing you cannot undo.

Payments are the area still in progress. A deployment made this week would have put partly-finished billing code onto a real server. The risk is not an ugly screen — it is charging a customer the wrong amount, taking money and not activating the account, or failing to refund. Those are mistakes that cost trust and money, and they are not fixable with a quick patch.

2. Deploying mid-development means deploying repeatedly.

The system is changing daily. A deployment made on the 10th would have been out of date by the 12th and wrong by the 15th. Each redeployment carries its own risk of breaking something. Doing it once, at the right moment, is both safer and cheaper than doing it four times.

3. The attempt surfaced real problems — which is exactly why it was worth doing.

  • The server refused to start at all unless an optional background service was running — a fault that would have caused a total outage on the very first live deployment. Found and fixed.
  • A settings file was one step away from having live passwords committed into the project history, where they are extremely hard to remove. Closed.
  • The automatic coding-test feature cannot run on ordinary hosting — it needs a machine of its own. Discovered during this attempt, and I corrected my own earlier assurance to you on that point rather than letting it fail quietly later.

Had we pushed the deployment through on the 10th, the first two would have hit you on day one.

4. The starting point was materially worse than anyone knew.

The 10th was estimated before the full review existed. That review then found the app would not build, payments were fictional, and a stranger could log in as your administrator. Deploying to that date would have meant putting an insecure, non-functional product on your live domain. The right call was to fix the foundations first — and that is what the last month bought.

5. The work is not behind — the deployment was resequenced.

In the same month, five of nine areas were completed and verified, 30 of 44 known problems were closed, and payments went from entirely fake to genuinely working. The date moved because we reordered the last step, not because progress stalled.

In the meantime, your public site is already live

The public-facing website is deployed and reachable on your main domain right now. What is pending is the full production deployment of the system behind it — the server, the database and the AI services — which is what makes the logged-in product work at scale.

Nothing built for the deployment attempt was wasted. The packaging, the release process, the demo accounts and the hosting guide are all finished, committed, and will be used as-is when we deploy for real.
