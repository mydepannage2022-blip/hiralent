## Addendum (23 July) — Adversarial re-review caught two real issues, both fixed
Before signing off the foundation, we deliberately re-reviewed the whole batch of changes as if a hostile outside auditor were trying to break it — "assume it's wrong until proven otherwise." Two genuine problems surfaced, and both are now fixed and verified:

- **A privacy/access-control gap was closed.** An earlier change had correctly locked *one* candidate screen so a logged-in user could only see their **own** data — but six sibling screens (profile summary, skills, completeness, headline, and two data-update actions) had been left open, meaning one candidate could have viewed, or even altered, **another** candidate's information by changing an id in the address. We applied the same ownership check to **all** of them through a single shared rule, and upgraded our automated test to prove every one of the eight is now locked (previously it only checked the one). *Note: strictly this is "security" work that belongs to the next phase — but since a partial fix was already in this batch, leaving it half-done behind a green checkmark was the more dangerous option, so we finished it now and documented the decision.*
- **A hidden "works on my machine" trap was removed.** One screen quietly relied on two software libraries that were installed on the current machine but **never officially listed** in the project. It built fine here, but a brand-new setup (or the live server) would have failed. We've now formally listed them at their exact current versions and confirmed a clean, from-scratch install succeeds — so the "repeatable setup" guarantee is now genuinely true.

All 11 automated checks (excluding the machine-specific end-to-end one) pass after these fixes. No user-facing behaviour changed; these were correctness and safety fixes.

## Addendum 2 (23 July) — Security hardening begins: passwords & keys

The foundation phase is closed and **Wave 1 (security hardening) has started**. Its first job — deliberately first, because everything else is pointless until it's done — is to treat **every password and access key in the project as already leaked** and replace them.

**What we found and fixed**
- **A guessable master password for administrator accounts.** If one setting was missing on a server, the system quietly fell back to a fixed, publicly-visible password written into the code — in two separate places. Anyone who read that code could have issued themselves a valid **super-administrator** pass. Removed; the system now refuses to start at all if a proper secret isn't configured, rather than silently using a weak one.
- **A live AI-provider key was written into the code itself** (and is therefore in the project's history). Removed from the code — but see "what I need from you" below, because **the key stays active until it's cancelled at the provider**.
- **A shared "service password" was hard-coded** into one of the AI services and into its deployment file — which was marked as a *production* configuration. Removed from both.
- **A full set of storage credentials was hard-coded** into one upload screen, along with a duplicate storage connection carrying its own second copy of credentials. Both removed; that screen now uses the project's single, properly-configured storage connection.
- **A service password was being written into the server logs in plain text.** Removed.
- **All the passwords we generate ourselves have been replaced** with new, very strong random values.
- **Automatic leak detection is now in place.** Two independent checks now run: one on every code push, one in our standard test suite. If anyone ever pastes a password or key into the code again, it gets caught immediately. We deliberately tried to sneak an old password back in to confirm the check actually fires — it did.

**One side effect, by design:** because the login passwords were replaced, **everyone currently signed in has been signed out** and will need to log in again. That is exactly what "invalidate the old keys" means — it is intended, not a fault.

**What this means for you**
- No visible feature changes. This is the difference between a system that *looks* secure and one that is — an administrator password that anyone could read from the code is a complete bypass of the login system, and a published AI key is billable to you by whoever finds it.

**⚠️ Anything I need from you — this part I cannot do for you**
The keys that belong to **outside providers** must be cancelled and re-issued from inside those providers' own dashboards, using your accounts. I've written a step-by-step guide (each provider, exactly what to click, where the new value goes, and how to confirm the old one is dead). I need you to run through it for:
- **Google AI (highest priority — this is the key that was published in the code)**
- Pinecone · Cloudinary · the email/SMTP account · Firebase · and any shared storage server

**Until the Google AI key in particular is cancelled, it is still live and still usable by anyone who has seen the code.** Everything on our side is ready; this is the one remaining step, and it's about 20–30 minutes of dashboard work.
