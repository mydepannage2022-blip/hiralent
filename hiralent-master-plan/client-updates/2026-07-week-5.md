## Addendum (23 July) — Adversarial re-review caught two real issues, both fixed
Before signing off the foundation, we deliberately re-reviewed the whole batch of changes as if a hostile outside auditor were trying to break it — "assume it's wrong until proven otherwise." Two genuine problems surfaced, and both are now fixed and verified:

- **A privacy/access-control gap was closed.** An earlier change had correctly locked *one* candidate screen so a logged-in user could only see their **own** data — but six sibling screens (profile summary, skills, completeness, headline, and two data-update actions) had been left open, meaning one candidate could have viewed, or even altered, **another** candidate's information by changing an id in the address. We applied the same ownership check to **all** of them through a single shared rule, and upgraded our automated test to prove every one of the eight is now locked (previously it only checked the one). *Note: strictly this is "security" work that belongs to the next phase — but since a partial fix was already in this batch, leaving it half-done behind a green checkmark was the more dangerous option, so we finished it now and documented the decision.*
- **A hidden "works on my machine" trap was removed.** One screen quietly relied on two software libraries that were installed on the current machine but **never officially listed** in the project. It built fine here, but a brand-new setup (or the live server) would have failed. We've now formally listed them at their exact current versions and confirmed a clean, from-scratch install succeeds — so the "repeatable setup" guarantee is now genuinely true.

All 11 automated checks (excluding the machine-specific end-to-end one) pass after these fixes. No user-facing behaviour changed; these were correctness and safety fixes.

## Addendum 2 (23 July) — Security hardening begins: passwords & keys

The foundation phase is closed and **Wave 1 (security hardening) has started**. Its first job — deliberately first, because everything else is pointless until it's done — is to treat **every password and access key in the project as already leaked** and replace them.

**What we found and fixed**
- **A guessable master password for administrator accounts.** If one setting was missing on a server, the system quietly fell back to a fixed, publicly-visible password written into the code — in two separate places. Anyone who read that code could have issued themselves a valid **super-administrator** pass. Removed; the system now refuses to start at all if a proper secret isn't configured, rather than silently using a weak one.
- **A live AI-provider key was written into the code itself** (and is therefore in the project's history). Removed from the code — but see "what I need from you" below, because **the key stays active until it's cancelled at the provider**.
- **A shared "service password" was hard-coded** into one of the AI services and into its deployment file — which was marked as a *production* configuration. Removed from both.
- **A full set of storage credentials was hard-coded** into one upload screen, along with a duplicate storage connection carrying its own second copy of credentials. Both removed; that screen now uses the project's single, properly-configured storage connection.
- **A service password was being written into the server logs in plain text.** Removed.
- **All the passwords we generate ourselves have been replaced** with new, very strong random values.
- **Automatic leak detection is now in place.** Two independent checks now run: one on every code push, one in our standard test suite. If anyone ever pastes a password or key into the code again, it gets caught immediately. We deliberately tried to sneak an old password back in to confirm the check actually fires — it did.

**One side effect, by design:** because the login passwords were replaced, **everyone currently signed in has been signed out** and will need to log in again. That is exactly what "invalidate the old keys" means — it is intended, not a fault.

**What this means for you**
- No visible feature changes. This is the difference between a system that *looks* secure and one that is — an administrator password that anyone could read from the code is a complete bypass of the login system, and a published AI key is billable to you by whoever finds it.

**⚠️ Anything I need from you — this part I cannot do for you**
The keys that belong to **outside providers** must be cancelled and re-issued from inside those providers' own dashboards, using your accounts. I've written a step-by-step guide (each provider, exactly what to click, where the new value goes, and how to confirm the old one is dead). I need you to run through it for:
- **Google AI (highest priority — this is the key that was published in the code)**
- Pinecone · Cloudinary · the email/SMTP account · Firebase · and any shared storage server

**Until the Google AI key in particular is cancelled, it is still live and still usable by anyone who has seen the code.** Everything on our side is ready; this is the one remaining step, and it's about 20–30 minutes of dashboard work.

## Addendum 3 — Logins, sessions & "log out actually logs you out" (Session 10)

The second security job is done: making the **login and session system genuinely enforce itself**. Before this, several protections looked present but weren't actually working.

**What we found and fixed**
- **"Log out" wasn't really logging anyone out.** Because of a mismatch in how login tokens were stored versus checked, ending a session (or logging out) quietly did nothing on the server — the old token kept working. This is now fixed and **proven**: after logout, the token is rejected on the very next request.
- **Access passes now expire quickly instead of lasting a week.** Previously, if someone's login token was ever stolen it stayed valid for **7 days**. Now it lasts about **15 minutes** and the app silently renews it in the background, so you stay logged in normally but a stolen token is near-useless within minutes. If you sign out everywhere, that renewal stops immediately.
- **Tokens can no longer sneak past the guard.** There was a loophole that let certain tokens through without a real session behind them; that loophole is closed, and every request now confirms the session is still live.
- **Renewal passes are single-use.** Each background renewal issues a brand-new pass and cancels the old one, so a captured renewal pass can't be reused.
- **Two weak "random" values were hardened** — the temporary password we generate for new agency accounts, and an internal device fingerprint — both now use proper cryptographic randomness.

**How we know it's real:** we built an automated test that spins up the actual system and checks each of these end-to-end — forged token rejected, logout truly revokes, renewal works but old passes die, expired sessions blocked. All pass, and the checks now run as part of our standard suite so they can't silently break later.

**What this means for you**
- No visible change day-to-day — you log in and use the app exactly as before. The difference is that "secure" is now enforced by the server rather than assumed.
- One deliberately-postponed item: a specific end-to-end email-based login test needs a test mail server to be set up; we've noted it for a later session. The core login path is already covered by the automated test above.

## Addendum 4 — Locking every door: "your data is yours only" (Session 3)

The third security job is done: making sure **every screen and action checks who you are, and that people can only reach their own data**. The login system was now solid — but a login only protects a door if that door is actually *locked*. We went through the whole application and found several doors that were closed but unlocked.

**What we found and fixed**
- **Anyone could read anyone's CV.** Uploaded CVs/resumes were served from a public web address — if you knew (or guessed) the link, you could open any candidate's CV with no login at all, and the link never expired. Now CVs are only reachable through a **short-lived, signed link** that the system hands to a logged-in user and that stops working after a few minutes. The old public address now returns "not found".
- **Coding-test submissions could be read by the wrong person.** A candidate's test submission could be fetched — and its live results watched — just by knowing its id, with no ownership check. Worse, when creating a submission the system trusted a "who am I" value sent by the caller, which could be faked. Now a submission is always tied to the **actually-logged-in** person, and only that person can read it or watch its live results.
- **Six administrator screens were completely open.** The screens that approve or reject relocation agencies had **no protection at all** — in principle anyone could have approved or rejected an agency. They're now behind the same administrator login as the rest of the admin area.
- **An unprotected screen could mark a company "verified".** A behind-the-scenes step that finalises a company's verification could be triggered without logging in. Locked.
- **The document-validation callback was unauthenticated.** An outside AI service reports document-check results back to us; that channel had no password, so anyone could have sent fake "this document passed" results. It now requires a shared secret, and the AI service was updated to send it.
- **The document-upload/scan endpoint was open and unlimited.** It accepted files and ran heavy processing with no login and no size limit. Now it requires login, caps the file size, and only accepts document/image types.
- **Several data and analytics screens** (assessment answers, results insights, the question bank list) were missing their login check. All added.
- **We wrote down every page that is *meant* to be public** (health check, sign-up, login, public company/candidate pages, etc.) with the reason each one is safe — so "open on purpose" is now a reviewed, documented list rather than an accident.

**How we know it's real:** we built an automated test that starts the actual system and checks each of these end-to-end — the callback rejects a missing password, one user is blocked (with the correct "forbidden" response) from reading another user's submission and live results, faking the "who am I" value doesn't work, the old public CV address is gone while a signed link works and then expires, and every newly-locked screen refuses an unauthenticated visitor. All pass, and this new test now runs as part of our standard suite (**now 15 automated checks, all green**).

**What this means for you**
- No visible change to how the app is used. The difference is that "only you can see your data" is now enforced on every screen we found, not just assumed.

**Session close — three more gaps closed to finish the job cleanly**
- **A cross-company leak in "recompute a company's insights."** That action only checked you were logged in, not *which* company you belong to. Fixing it revealed the shared "are you a member of this company?" check was itself faulty two ways — it rejected genuine company members by mistake, **and** it let one company's admin reach another company's data. Both fixed: platform admins aside, you can only touch your own company's data.
- **Résumés no longer visible without login.** The public candidate profile page had been handing anonymous visitors a link to the candidate's CV. Since a CV contains personal contact details, we removed the CV from that public page entirely — it's now only reachable once you're logged in.
- **The live "run my code" screen no longer puts your login key in the address bar.** Because of a browser limitation, the live-results stream had been carrying your session token in the page address. We switched it to a tiny, single-purpose pass that only unlocks *that one* code run and expires within minutes — so even if that address leaked, it can't be used to reach your account.

Automated checks re-run after all of this — **still 15/15 green** (and the code-runner's live updates were re-tested end-to-end through the new ticket step).

## Addendum 5 — Stopping submitted code from touching our server (Session 4)

This was the most serious remaining security item. When a candidate takes a coding test, their code has to actually run somewhere. The safe way is to run it inside a sealed, throwaway "sandbox" container with no network and no access to the real machine. We found that if that sandbox wasn't available, the system would quietly **fall back to running the candidate's code directly on our own server** — and there was also a small helper service that would run *anyone's* code with no password at all. In practice that means a malicious candidate could potentially run their own commands on our infrastructure.

**What we changed**
- **No more running code on the server.** If the secure sandbox isn't available, the test now simply **fails safely** ("couldn't run — no secure runner") instead of falling back to the unsafe path. Running code directly on the machine is now only possible with a deliberate developer switch that is **impossible to turn on in production** — the app refuses to even start if someone tries.
- **The sandbox is now properly locked down.** The container runs as a restricted (non-administrator) user, can't write to its own filesystem except a scratch area, can't gain new privileges, has its process count and memory capped, and has no network — the standard "defense in depth" settings that were missing.
- **The code-running helper now needs a password.** That internal service will no longer run anything without a shared secret key, and refuses to operate at all if the key isn't set.
- **Closed a smaller input-handling weakness** in how test inputs were passed to the program.

**How we know it's real:** a new automated test (no special setup needed) proves the container is always launched with every lockdown setting, that the "run on the server" path is refused in production, and that the helper service rejects unauthenticated calls. Our full suite is now **16 automated checks, all green**.

**One honest note:** the container-lockdown settings are verified by the test, but a final real-world dry-run of a compiled-language submission (C#/Java/C++) inside the tightened container is best done on a machine with the sandbox engine installed — noted as a quick follow-up, not a blocker.

## Addendum 6 — Hardening the front door: headers, trusted origins & flood protection (Session 5)

With the login system, per-user data locks, and code sandbox all done, this session hardened the **outer edge** of the server — the part every browser and every attacker touches first. Think of it as the building's front entrance: the locks inside were fixed in earlier sessions; this was about the entrance itself.

**What we found and fixed**
- **The server sent no safety instructions to browsers.** A modern server is supposed to tell each visitor's browser things like "only ever talk to me over a secure connection" and "don't let other sites frame or impersonate my pages." Ours sent none of these. We added the industry-standard set of protective headers, so browsers now enforce these rules automatically.
- **The server trusted too many origins.** The rule for "which websites are allowed to call this server on a logged-in user's behalf" was hard-coded and loose. It's now a clean, configurable allowlist — only the sites we approve can make credentialed calls, and unknown sites are turned away. (One of the AI helper services had the most permissive possible setting — "allow everyone" — which we also tightened.)
- **There was almost no flood protection.** Only two minor pages limited how often they could be hit; **login, sign-up, file-scanning, and the expensive AI features could be hammered as fast as an attacker liked** — the raw material for password-guessing and for running up AI costs. We added rate limiting across the whole server, with **stricter caps on the sensitive/expensive endpoints** (login, document scanning, code submissions, AI features). Crucially, these limits are **shared across servers**, so adding more servers later won't accidentally multiply the allowance — an attacker can't dodge the limit by spreading requests around.
- **The server would accept an unlimited-size request body.** A single oversized request could have been used to exhaust the server's memory. We now cap request sizes and reject anything too large with a clear "payload too large" response.

**How we know it's real:** a new automated test starts the actual server and confirms every protective header is present, that an un-approved website is refused while an approved one is allowed, that an oversized request is rejected, and that hammering the login endpoint past its limit gets blocked. It also re-confirmed the earlier work still functions under the new rules (CV links and live code-run updates, which cross between sites, keep working). Our full safety suite is now **17 automated checks, all green**.

**One honest note:** the "shared across servers" flood limit is proven in principle and switches on automatically the moment the shared coordination service (Redis) is running; on this particular machine that service wasn't available, so that one sub-check ran in "skip and report" mode rather than live. The single-server flood protection is fully proven. This is the same kind of "needs a specific engine running to dry-run live" follow-up noted for the code sandbox — not a blocker.

**What this means for you**
- No visible change to how the app is used. The server is now much harder to abuse from the outside: harder to brute-force, harder to run up costs on, and it instructs every visitor's browser to behave safely.

## Addendum 7 — Closing two side doors: fake test data & the AI back-office (Session 6)

Previous sessions locked the front entrance. This session closed two **side doors** that a savvy user (or anyone who could reach our internal machines) could have slipped through.

**What we found and fixed**
- **A leftover "test results" shortcut anyone could use.** The app had a developer-only endpoint that would accept a made-up assessment result and write it straight into the database — with **no login required**. It was meant for local testing, but it was still shipping in the product. We **deleted it entirely**, along with an unused "pretend I'm an administrator" helper and a similar "simulate competition results" shortcut that any logged-in user could have used to **fake leaderboard scores**. The one legitimate testing tool that remains now physically cannot switch on in production.
- **Our AI helper services had no lock on their door.** Behind the scenes, the main app hands work to several specialised AI services (reading job descriptions, validating documents, generating questions, checking CVs). Until now, **any of those services would do work for anyone who could reach it** — they didn't ask "are you really our app?" We gave every one of them a **shared secret handshake**: the main app now presents a private token on every internal request, and each AI service refuses to do anything without the correct token. Importantly, if that token is ever missing by mistake, the services **refuse all work** rather than quietly accepting everyone — the safe default. One of these services previously had a lock that **silently did nothing** when misconfigured; we fixed it to fail safe.
- **No secrets in the logs.** We removed a log line that ran on every internal call, eliminating any chance of an internal token being written into plain-text logs.

**How we know it's real:** two new automated tests. The first confirms the fake-data and simulate shortcuts are gone and that the remaining dev tool is blocked outside a developer's own machine. The second actually **runs each AI service's real security check** and proves that a request with **no token or a wrong token is refused**, a correct token is accepted, health checks stay open, and a **misconfigured service refuses everyone** rather than letting them in. Our full safety suite is now **19 automated checks, all green** (up from 17).

**One honest note:** the AI-service security checks are exercised against each service's real security code in a lightweight test harness rather than a full production-style launch of every service (those pull in heavy AI libraries). One additional AI service that the main app doesn't currently call was left for a later pass and is noted as a follow-up, not a gap.

**What this means for you**
- No visible change to how the app is used. Two more ways to tamper with data or abuse our internal AI services are now closed, and our internal services only trust our own app.

## Addendum 8 — Security sign-off: proving every door, for every kind of user (Session 7)

The previous sessions fixed the locks one by one. This session's job was different: **prove the whole
security layer actually holds, end-to-end, and sign off on it** before we move on to building features.
Think of it as the final inspection of the building's security before handing over the keys.

**What we did**
- **Tested every kind of user against every sensitive screen.** We created a real account of each type —
  a candidate, a company administrator, a relocation-agency admin, and a super-administrator — and then
  checked, live, that each one gets exactly the right answer on the important screens: **no login → turned
  away; wrong type of user → forbidden; the correct user → allowed in.** All 21 of these checks pass. This
  is now an automated test, so it can't silently break later.
- **Caught and fixed a brand-new hole in the process.** While building that test we discovered the sign-up
  form would let someone register themselves *as an administrator* just by tampering with the request —
  which would have handed them access across every company. We closed it (sign-up can now only create the
  three normal account types) and added a test that proves the trick no longer works.
- **Cleaned up the software "ingredients" list.** Every project is built on dozens of third-party
  components, and some had known security flaws. We updated them: the server went from **63 serious/critical
  flaws down to 1**, and the website from **20 down to 0**. The single remaining one has no fix available
  from its maker yet (it comes bundled inside Google's Firebase toolkit) — it's documented and scheduled for
  the deployment wave. The app still builds cleanly after all the updates.
- **Made sure our secrets won't get baked into shipped copies of the app.** When we package the app for a
  server, there's a risk of accidentally including the file that holds passwords and keys. We found three
  services that would have done exactly that, fixed them, and added an automatic check that will catch it if
  anyone reintroduces the mistake.
- **Wrote the security "map" for the final go-live review.** A per-user-type summary of what each type can
  touch, the risks that matter for them, and exactly how each is protected — the document the final
  production sign-off will work from.

**What this means for you**
- **The security phase is now proven, not just built.** Every serious and high-priority security risk we
  set out to fix has been re-tested by actually trying the original attack and confirming it now fails.
  There were no visible changes to how the app works — this was about making "secure" demonstrable.

**Still needs you / noted for later (unchanged from before):** the outside-provider keys still need to be
cancelled and re-issued from your dashboards (the Google AI one especially). A couple of checks that need a
specific engine running (the code sandbox and a full packaged-image scan) are scheduled for the deployment
wave — they're set up and ready, just waiting on that environment.
