## What got done this period

**We made it possible to stand up a fresh, working system from nothing — and made the setup safe to run against a live database.**

Until now, setting up a new copy of the app (for staging or for going live) was a minefield. Three problems:

1. **Nobody could get in as an administrator.** There was no step that created an admin account, no permissions data, and — we discovered while testing — even the admin login page was being blocked by a mis-ordered security gate, so *even if* an admin existed they couldn't log in. The platform had, in effect, no way for the owner to administer it.
2. **The setup routine was dangerous.** The script that populates a new database would **erase** the existing pricing plans every time it ran, and would **duplicate** sample data on each run. Run it twice and you'd have double the data; point it at a live database and it could wipe real records.
3. **Nothing confirmed the database structure could even be built from scratch.** The app's database is built up from 57 sequential change-scripts. Nobody had proven they still apply cleanly to an empty database.

We fixed all three:
- **A fresh database now comes up complete:** pricing plans, achievement badges, a working **administrator account**, and a full **permissions matrix** (every role's access to every part of the app). We also fixed the login-gate ordering bug, so the administrator can actually sign in.
- **The setup routine is now safe to re-run and safe for production:** it only ever *adds or updates* — it never erases. Running it ten times leaves exactly the same result as running it once. In production it refuses to load sample/demo data and refuses to create an admin with a guessable default password.
- **We proved the 57-step database build works** by building a throwaway database from scratch, running all 57 steps, and confirming every one applied — all without ever touching the real database.

**How we know it's real (not just "we wrote the code"):** we built two automated tests that do the whole thing end-to-end against a real database — create a fresh throwaway database, build its structure, run the setup, then **actually log in as the new administrator and confirm it succeeds**. They also run the setup a second time and confirm nothing duplicated, and run it in "production mode" to confirm it loads no demo data and wipes nothing. Everything passes, and the throwaway databases are cleaned up automatically.

Our full automated safety suite is now **27 checks, all green** (up from 25).

**We also made the busiest parts of the database fast at scale.**

The app's heaviest tables — chat messages, coding-test submissions, activity analytics, communication logs, and the admin audit trail — had **no database indexes**. An index is like the index at the back of a book: without it, the database has to read *every* row to answer a question ("show this conversation's messages, newest first"), which is fine with a few hundred rows but crawls once there are millions. We added **36 targeted indexes** across the 22 busiest tables, each matched to the exact questions the app actually asks.

**How we know it's real (not just "we added indexes"):** databases don't always *use* an index — on a tiny table it's actually faster not to. So we built an automated test that loads a throwaway database with **20,000 rows per table**, runs the app's real hot queries, and inspects the database's own execution plan to **confirm each query now uses its index** — and, as a control, confirms a query on a *non-indexed* column still does the slow full scan. All five proved fast; the control proved slow — so the speed-up is real and measured, not assumed. This ran entirely on disposable databases; the real one was never touched. That brings the automated suite to **28 checks, all green**.

**We also capped how much a single request can pull from the database — and set old data to clean itself up.**

Some screens fetched *everything* in one go — every conversation, every job applicant, every case — with no upper limit. With a few hundred rows that's fine; with hundreds of thousands it can choke the server and the network on a single click (and it's a way for a bad actor to hammer the system). We put a hard ceiling on the busiest list screens so a request can only ever return a bounded chunk, no matter what it asks for — and we did it **without changing anything visible**: for normal-sized accounts the screens behave exactly as before. We also removed a wasteful pattern on the company dashboard that loaded every application just to count them, replacing it with a direct database count.

Separately, several "firehose" tables (activity analytics, communication logs, the audit trail, expired login tokens/sessions) grow forever and nothing ever cleaned them up. We added an **opt-in automatic cleanup** that deletes rows past a set age — **off by default**, so it can never delete anything on a system that hasn't deliberately switched it on.

**How we know it's real:** an automated test boots the actual app against a throwaway database, creates a user, loads it with far more rows than the cap allows, then hammers the endpoint asking for 99,999 rows — and confirms it gets back only the capped amount, with the true total reported in the response. Another test seeds a firehose table with a mix of old and recent rows, runs the cleanup once, and confirms **only the old rows were deleted, the recent ones untouched**. That brings the automated suite to **29 checks, all green**.
