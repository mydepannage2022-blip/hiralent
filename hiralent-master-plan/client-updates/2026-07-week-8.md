## What got done this period

**The biggest fix: deleting an account now actually works — and it didn't before.**

When a company or agency account tried to delete itself, the deletion **failed halfway and errored out**. The reason was a gap in the database's "what happens to related records when the parent is removed" rules: for six important record types (a company's profile, its conversations, its messages, team invitations, and its activity log) the database had **no instruction** for what to do, so it defaulted to *"refuse the deletion entirely."* The result: those accounts simply could not be deleted. This is both a broken feature and a legal problem — under privacy law ("right to erasure") a user is entitled to have their data actually removed.

We went through **all 142 relationships** in the database and gave every one an explicit, deliberate rule:
- **Owned data is removed with the account** — a company's profile, its job posts' applications, a candidate's documents and certifications, direct-message threads, and so on. When the account goes, its own data goes with it.
- **Shared audit/history records are kept, but the personal link is erased** — e.g. an activity-log entry or a team invitation stays for record-keeping, but the reference to the deleted person is blanked out. This is exactly the privacy-law balance: remove the personal data, keep the anonymized business record.
- **Reference data is protected** — you can't accidentally delete a pricing plan or an achievement badge that's still in use.

**How we know it's real (not just "we wrote the rules"):** we built an automated test that, on a throwaway database, creates a full company account **with** a profile, conversations, messages, an activity log and a team invitation, then **deletes it and confirms the deletion succeeds** — the owned records are gone, and the audit records survive with the personal reference correctly blanked. It does the same for a candidate account. Before this change that deletion errored; now it passes.

**Postal codes now accept international formats.**

The postal-code field only accepted plain numbers, so a UK code like "SW1A 1AA" or any code with letters couldn't be entered. We switched it to accept text, on both the sign-up screen and the database, so applicants from any country can complete their profile.

**We removed dead weight from the system.**

- **Four unused database tables** were sitting in the schema doing nothing — two completely unused (a leftover question bank and an old chat table, both superseded), and one pair that was being *written to on every job application but never read back*. We removed them and the code that fed them.
- **An entire unused database engine (MongoDB)** was being connected at start-up but stored **zero data and was never read from** — pure leftover. Worse, if that engine was unreachable, the **live server would crash on start-up in a loop**. We removed it completely. The server now starts cleanly without it (proven), and we also cleared out a leftover live database password for it that was still sitting in the config.
- **Certifications had three copies** in the system that could drift out of sync. We made the proper certifications table the single source of truth and removed the duplicate copy, so what candidates see and what search finds can never disagree.

**How we know it's real:** an automated test builds a fresh throwaway database, confirms the four dead tables and the duplicate certification storage are actually gone, enters an alphanumeric postal code and confirms it's accepted, and **starts the real application server with the old database engine completely removed** — confirming it comes up healthy without it. Our automated safety suite is now **30 checks, all green** (up from 29).

## Addendum (29 July) — Data-layer gate: CLOSED (Session 7)

We also **closed the Wave 2 "gate"** this week — the formal sign-off that the whole database layer is not just individually correct, but works **end-to-end as one flow**.

Until now, each database improvement (safe upgrades, fresh-database setup, the admin-account seed, the speed indexes, the capped list pages, the bounded database connections) was proven **on its own**. This session we built a single automated test that runs the **entire path in one go, on a throwaway database**:

- start from a completely **empty** database,
- run all the setup steps and create the starter data and the **administrator account**,
- **log that administrator in** (full two-factor flow) — and confirm a wrong password is refused,
- hammer it with **30 simultaneous list-page requests** — confirming every page stays within its size limit, the total count is reported correctly, and the number of open database connections **stays capped** (uncapped connections are exactly what makes an app fall over under load),
- confirm a heavy query still uses its **speed index** at 20,000 rows,
- with the app reporting **healthy** the whole time.

We also added a **"does the alarm actually work?" test**: it deliberately re-introduces the exact mistakes we fixed earlier (an unbounded database connection; a shutdown call that would kill the shared connection pool) and confirms our safety checks **catch them and fail loudly**. A green check only means something if it turns red when something is broken.
