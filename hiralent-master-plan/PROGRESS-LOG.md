## 2026-07-27 — Wave 2 Session 2: bounded connection pooling + PgBouncer + directUrl  [Wave 2 / Phase 2.1]  (R-06b)
- **Before:** After S1 every process shared one Prisma singleton, but that singleton was `new PrismaClient()` with **no bound** — Prisma's default pool is `cpus*2+1` (≈17 on an 8-core box) **per process**, and there are **7 pooled processes** (1 API server + 6 workers). Under load that's ≈120 connections against Postgres's default `max_connections=100` → exhaustion. Migrations had no direct path (a problem once PgBouncer fronts the DB, since transaction pooling breaks DDL), and no pooler was defined anywhere.
- **Change:**
  1. **Risk-spike first (measurement harness):** the repo has **no `pg` client** — Postgres is only reachable via Prisma. Spiked a throwaway tsx probe to prove we could measure a live pool through `pg_stat_activity`. Confirmed: (a) `application_name` URL param **passes through Prisma 6.19** into `pg_stat_activity` → clean per-client isolation; (b) `connection_limit` **binds exactly** — swept limits 1/3/5/10 and peak active connections tracked the limit precisely (flood duration scaled inversely); (c) the `pg_sleep(x)::text` cast is required (bare `pg_sleep` returns `void` → Prisma deserialize error that silently swallowed the load). This locked the verifier design before touching config.
  2. **Bounded pool (URL params):** `backend/.env.example` `DATABASE_URL` now carries `?connection_limit=10&pool_timeout=20`. **Pool math** documented in-file: `(1 server + 6 workers) × 10 = 70 < 100` (~30 headroom for migrations/monitoring). `prisma.ts` intentionally **left untouched** (S1 export contract preserved; the bound is a config concern, enforced by a new verifier).
  3. **Direct migration path:** added `directUrl = env("DIRECT_DATABASE_URL")` to `schema.prisma` and `DIRECT_DATABASE_URL` (no pool/pgbouncer params) to `.env.example`. **Proven runtime-safe**: `prisma generate` and Prisma **Client boot both work with `DIRECT_DATABASE_URL` unset** (directUrl is migrate/validate-only) — so runtime and the build gate never regress; only `prisma migrate`/`validate` require it.
